# Собственное шифрование временных файлов Codex

Экспериментальная реализация для Windows. Это отдельная файловая система на
WinFsp с собственным форматом хранения, а не Cryptomator или BitLocker.
Монтирование и совместимость с Windows-песочницей **ещё не проверены на Windows**.
Не используйте её как единственное средство защиты до выполнения Windows-тестов.

## Как устроено

```text
Codex / дочерний процесс
    -> обычные файловые операции на T:\system-temp
    -> WinFsp + наш адаптер windows.py
    -> store.py: AES-256-GCM
    -> D:\CodexTempCiphertext\session-<случайный ID>\<случайный ID>.bin
```

- Содержимое и исходный путь входят в одну аутентифицированную зашифрованную
  запись. Имена физических объектов — случайные 128-битные идентификаторы.
  Открытого индекса соответствия имён на диске нет.
- Шифрование использует `cryptography`, без собственного криптографического
  примитива. Ключ генерируется заново для каждого запуска и не сохраняется.
- Каждая запись использует уникальный 96-битный счётчик nonce. Идентификатор
  объекта и номер его версии связаны с шифротекстом через AAD. Подмена между
  объектами и возврат старой версии обнаруживаются в пределах живой сессии.
- Чтение расшифровывает файл в памяти; перезапись создаёт только зашифрованный
  staging-файл, делает `fsync` и атомарную замену. Расшифрованных копий на диске
  сам модуль не создаёт.
- При повреждении шифротекста или ошибке backing storage хранилище переходит в
  состояние отказа; дальнейшие операции отклоняются. Обычного TEMP как
  запасного пути у реализации нет.
- Переименование, произвольные смещения, дописывание, усечение, регистронезависимый
  поиск и удаление файла с открытым дескриптором реализованы в ядре.

**Это временное хранилище:** после остановки процесса ключ теряется и файлы
восстановить нельзя. Каждый запуск создаёт новую пустую сессию. Старые каталоги
`session-*` остаются зашифрованными; после остановки соответствующей службы их
можно удалить обычным способом. Автоматического удаления неизвестных каталогов
нет. Базы и настройки Codex туда не переносятся.

## Установка на Windows

1. Установите [WinFsp](https://github.com/winfsp/winfsp/releases) с компонентами
   Developer. WinFsp обеспечивает доступ Windows к нашей файловой системе;
   шифрование выполняет наш процесс.
2. Нужен Python. Upstream `winfspy 0.8.4` заявляет Python 3.7–3.10;
   для первого Windows-теста используйте Python 3.10 x64. Если pip собирает
   привязку из исходников, потребуются C++ Build Tools.
3. В корне этого репозитория:

```powershell
py -3.10 -m venv tools\encrypted-temp\.venv
tools\encrypted-temp\.venv\Scripts\python.exe -m pip install --upgrade pip
tools\encrypted-temp\.venv\Scripts\python.exe -m pip install -e ".\tools\encrypted-temp[test]"
```

## Запуск

В первом PowerShell запустите службу. Буква `T:` должна быть свободна; backing
каталог должен находиться на обычном диске, вне виртуального диска:

```powershell
tools\encrypted-temp\.venv\Scripts\codex-encrypted-temp.exe `
    --backing D:\CodexTempCiphertext --drive T:
```

Служба остаётся запущенной. До её остановки закройте Codex и все дочерние
программы, использующие этот диск. `Ctrl+C` останавливает службу и снимает диск.
Принудительное завершение также теряет ключ и все временные данные.

Во втором PowerShell, из корня репозитория:

```powershell
.\tools\encrypted-temp\start-codex-encrypted.ps1 -Drive T: `
    -CodexExecutable C:\Tools\codex.exe
```

Запускатель проверяет тип файловой системы и метку диска, затем:

| Источник | Назначение |
| --- | --- |
| `TEMP`, `TMP`, `TMPDIR` процесса и наследующих его детей | `T:\system-temp` |
| `$CODEX_HOME\tmp` | junction на `T:\codex-tmp` |
| `$CODEX_HOME\.tmp` | junction на `T:\codex-dot-tmp` |
| Базы, сессии, конфигурация и остальная часть `CODEX_HOME` | прежнее расположение |

`CODEX_HOME` выбирается из окружения или `%USERPROFILE%\.codex`; его можно явно
передать через `-CodexHome`. Запускатель использует `--no-daemon`, чтобы не
подключиться к процессу со старым незашифрованным TEMP. Глобальные переменные
Windows не меняются; окружение PowerShell восстанавливается при выходе.

При первом запуске закройте **все** экземпляры Codex. Если `tmp` или `.tmp` уже
существуют как обычные каталоги, скрипт остановится без перезаписи. Их нужно
сначала отдельно перенести/переименовать после закрытия Codex. Старые данные при
этом не становятся зашифрованными и автоматически не удаляются.

Junction остаются после выхода. Если служба не запущена, это несуществующие цели,
а не созданные заново обычные каталоги. Перед каждым запуском нужен запускатель;
не назначайте эту букву другому диску. Проверка метки — защита от ошибки
конфигурации, не аутентификация против вредоносного администратора.

Для отката закройте Codex и службу. В Проводнике или PowerShell проверьте, что
`tmp` и `.tmp` действительно junction, удалите **только ссылки**, затем верните
исходные каталоги. Не применяйте рекурсивное удаление к целям junction.

## Точный охват и ограничения

Это не перехват всех записей Windows. Защищены только файлы, которые попадают
на наш виртуальный диск. В частности:

- В репозитории нет полной desktop-оболочки. Её кеш браузера, AppData, отдельные
  сервисы и уже запущенные процессы этим CLI-запускателем не перенаправляются.
- Программы могут игнорировать TEMP. Промежуточные файлы рядом с исходниками,
  `node_modules`, Git `.lock`, дампы, логи и кеши вне перенаправленных каталогов
  остаются там, где их создала программа.
- Codex также создаёт временные файлы рядом с постоянными файлами для атомарной
  замены, например в `rollout`, `config`, `secrets` и `core-plugins`. Они не
  охвачены. Простой перенос на другой том нарушил бы атомарность `rename`.
- `core-plugins/src/git_policy.rs::configure_trusted_git_repository` запрещает
  выход канонического `.tmp` за пределы `CODEX_HOME`. Перенаправление `.tmp`
  может блокировать соответствующие Git-операции плагинов. Защита не ослаблена.
- Права виртуального диска предоставляются текущему пользователю, SYSTEM и
  администраторам. Отдельные пользователи Windows-песочницы могут не получить
  доступ; проверка на целевой машине обязательна. Запускатель не отключает
  песочницу и не расширяет её права.
- Доступ к разблокированному диску позволяет читать открытые имена и данные.
  Администратор, память процесса, Windows pagefile, hibernation и crash dumps
  находятся вне защиты этого слоя. Python не гарантирует физическое стирание
  копий ключа/буферов из памяти.
- Размеры и время изменения физических объектов не скрыты. Полный откат
  состояния процесса/машины не защищён.
- Текущая реализация читает/перешифровывает **целый файл при каждой записи**.
  По умолчанию максимум 64 MiB на файл, 512 MiB суммарных логических данных и
  10 000 объектов. Пределы размера меняются флагами `--max-file-mib` и
  `--capacity-mib`; это не решение для больших сборочных кешей. Физический
  объём больше логического из-за метаданных и staging-файлов.
- ADS, hard links, reparse points и полная совместимость с NTFS не реализованы.

## Проверки

Переносимые тесты проверяют отсутствие открытых имён и содержимого в физических
объектах, операции файловой системы, конкуренцию, лимиты, подмену/усечение/
повтор шифротекста, ошибку атомарной записи и прекращение операций после отказа:

```powershell
tools\encrypted-temp\.venv\Scripts\python.exe -m pytest tools\encrypted-temp -q
```

Реальный тест драйвера запускается только явно, с неиспользуемой буквой диска:

```powershell
$env:CODEX_TEMP_TEST_DRIVE = 'T:'
tools\encrypted-temp\.venv\Scripts\python.exe -m pytest tools\encrypted-temp -q
```

Он монтирует нашу файловую систему, выполняет запись и чтение через Windows,
переименование, перечисление, `fsync`, удаление и работу отдельного Python-процесса
через TEMP. На macOS этот тест **пропускается**, а не имитирует драйвер.
После него отдельно необходим пробный запуск настоящего Codex с его песочницей
и инструментами. До этого совместимость с Codex на Windows не подтверждена.

Источники API: [WinFSPy](https://github.com/Scille/winfspy),
[AEAD в cryptography](https://cryptography.io/en/latest/hazmat/primitives/aead/).
